# Plan 01-01: SQLite Schema Migrations and Sector/Checklist Update APIs

This plan implements the backend foundation for Phase 1. It adds the nullable `sector` column to the SQLite `assets` table safely, creates the relational `asset_checklist` table, extends the data repository and service layers, and exposes the corresponding Next.js 16 dynamic API routes.

<threat_model>
### Security Threat Model (ASVS Level 1)

1. **SQL Injection (STRIDE: Tampering)**
   - *Threat*: Attackers try to inject SQL DDL/DML code via the dynamic route parameters (`ticker`) or request bodies (`sector`, `checklist.criterionId`).
   - *Mitigation*: Leverage parameterized bindings (`?`) in all `better-sqlite3` prepared statements. Never interpolate variables directly into SQL command strings.
2. **Input Validation Failures (STRIDE: Information Disclosure)**
   - *Threat*: Storing invalid sector text (too long, malformed) or invalid checklist status strings in the database.
   - *Mitigation*: Define strict Zod validation schemas in API controllers. Sectors must be trimmed strings (nullable). Checklist statuses must strictly match the enum `["yes", "no", "unsure"]`.
3. **Dynamic Route Parameter Parsing (STRIDE: Denial of Service)**
   - *Threat*: In Next.js 16, accessing `context.params.ticker` synchronously throws errors or fails under stress due to the promise resolution model.
   - *Mitigation*: Always type `context.params` as `Promise<{ ticker: string }>` and asynchronously await the values before executing lookup or storage operations.
</threat_model>

   - Invokes `repo().getChecklist(ticker)`.

   - Uses `db.transaction()` to atomically execute updates.
   - Loops over the items and calls `repo().upsertChecklist(ticker, item.criterionId, item.status)`.
</action>
